# GoMusic 26.11.85

## 私聊缓存：先缓存、再增量补新消息

**进入会话不再白屏等网络**：`openChat()` 先从本地 `SharedPreferences` 按 uid 读出该会话的历史消息，立刻按「最老在上、最新在下」铺出来，然后才发 `/msg/private/history`。缓存每个会话最多 400 条，关闭会话与每次刷新都会落盘，重开应用也在。

**只新增，不替换**：网络回来后把结果**合并**进已有列表（按 `id` 去重，没有 id 的用 `time + 发送方 + 正文 + 资源 id` 作稳定 key），不再像上一版那样 `chatMessages = list` 整体覆盖。这样首页只返回最近 30 条时，之前翻页翻到的老消息不会被冲掉；「加载更早」翻到的页也会留在列表里。

**顺序统一**：所有来源（缓存 / 首页 / 翻页）合并后统一按 `time` 升序、`id` 做同刻兜底排序，最老一条在最上、最新一条在最下；列表尾部不再挂「加载更早」，改到顶部；消息 item 带稳定 key，翻更早的页不会把视图弹回顶部；滚动跟随的是「最新一条」而不是列表长度，缓存先出、网络补新消息都能滚到底。

## 清除新消息提醒

三个层面一起处理，避免红点复活：

- **本地立即清**：打开会话就把该会话 `unread` 置 0，顶部「私信 N · 通知 M」扣掉这个会话的未读数。
- **已读基线持久化**：记下打开时该会话最新一条消息的时间（兼容秒级时间戳）。`/pl/count` 与会话列表的服务端未读数经常滞后，下次 `loadSocial()` 刷新时按基线把「已经看过的那批未读」从计数里扣掉、把对应会话红点归零；**有新消息时会话 time 超过基线，提醒会自动恢复**，不会永久屏蔽。
- **尽力通知服务端**：best-effort 调一次 `/msg/private/read`（标准模块里没有这个路由，失败静默忽略；实际清未读主要靠 `/msg/private/history` 本身 + 本地基线），不因接口不存在报错或卡住页面。

每次刷新聊天还会把已读基线推进到当前最新一条，边聊边收到新消息也不会在返回列表时冒出旧红点。

## 说明与限制
- 这轮附带的接口文档链接资源解析服务全部失败，标准模块目录里确认没有独立的「标记已读」接口，因此服务端侧只能尽力而为，清提醒以本地基线为准，以 CI 编译＋签名校验为准，未做实机联网验收。
- 缓存按 uid 存于应用私有存储；卸载应用或清除数据会清空，服务端仍是消息本体来源。
